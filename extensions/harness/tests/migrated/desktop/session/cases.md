# Batch 4b case rows: desktop session surface

The 145 `port` rows of batch 4's second lane (catalogue areas Session UI and Application end-to-end, batch 4; 45 of them need a display), each replaced by one row per reference case, following core `documentation/future/harness/testing/04-test-migration.md` sections 2 and 5. Written by lane S2-C3b; the integrator publishes the counts.

- `id` is the parent row's id with a `.cN` suffix, N being the case's position in its file (in file order, counting every case the file declares). `source` is the reference path at the pinned tag and that position; no reference test text is reproduced. Where one file is split over several catalogue rows, the cases are assigned to the row whose scope they fall under; only the cases of this lane's rows are listed.
- `behaviour` states, in this crate's words, what the target test asserts; `—` where no test asserts the case (the parent row's catalogue statement applies).
- `target` names the Rust test in this crate (`migrated-desktop-session::<module>::<test>`).
- `state`: `passing` (the test runs and passes); `ledger` (the harness behaves differently or lacks the behaviour: the test asserting the reference behaviour carries `#[ignore = "parity ledger: …"]`, or, where no test can express it, `note` states the difference; a target listed on a ledger row asserts the part that holds); `tour` (needs a display: not asserted, recorded as a state on `extensions/harness/tests/tour/states.txt` and checked by a person, `note` names the state).
- A case the shell has no stage for, or that tests the reference's own machinery, is `not-applicable` with its reason (`no-feature:` / `reference-internal:`), as in batch 4a.
- Generated or table-driven reference cases are one row per generator.
