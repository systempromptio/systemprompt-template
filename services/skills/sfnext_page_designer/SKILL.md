# Page Designer Skill

This skill covers Page Designer integration in Storefront Next — building merchant-editable pages with React components, decorators, and the Shopper Experience API.

## Overview

Page Designer is Commerce Cloud's visual editor for merchants. In Storefront Next, page structure (regions, components, attributes) is fetched from the Shopper Experience API and rendered via a component registry and `<Region>` component.

| Concept | Role |
|---------|------|
| **Page** | Fetched in route loaders via `fetchPageFromLoader(args, { pageId })` |
| **Region** | Named area rendered with `<Region page={...} regionId="..." />` |
| **Component** | Content block with a `typeId` and attributes; registered in `@/lib/registry` |
| **Registry** | Static registry auto-generated by Vite plugin — do not edit by hand |

## Which Pages Use Page Designer

| Uses Page Designer | Does Not |
|--------------------|----------|
| Home (`homepage`), Category/PLP, Search, Product/PDP | Cart, Checkout, Account, Auth |

## Route Setup

### In the Loader

```typescript
import { fetchPageFromLoader, collectComponentDataPromises } from '@/lib/page-designer';

export function loader(args: LoaderFunctionArgs) {
    const pagePromise = fetchPageFromLoader(args, { pageId: 'homepage' });
    const componentData = collectComponentDataPromises(args, pagePromise);

    return {
        page: pagePromise,
        componentData,
    };
}
```

### In the Layout

```typescript
import { Region } from '@/components/region';

export default function HomePage({ loaderData: { page, componentData } }) {
    return (
        <div>
            <Region page={page} regionId="hero" componentData={componentData}
                fallbackElement={<HeroSkeleton />}
                errorElement={<RegionError />} />

            <Region page={page} regionId="content" componentData={componentData}
                fallbackElement={<ContentSkeleton />} />
        </div>
    );
}
```

## Component Setup

### File Location (required)

**Every Page Designer component lives under `src/components/pd/`.** A PD component is any module that carries a `@Component(...)` decorator. Put each one in its own folder:

```
src/components/pd/<component-name>/index.tsx   # @Component + React render + default export
```

- One folder per component (e.g. `src/components/pd/hero/`, `src/components/pd/flyout-link-row/`). Group a related family under a subfolder when it has sub-components (e.g. `src/components/pd/global-footer/<part>/`).
- Do **not** co-locate PD components with consuming feature code (e.g. `src/components/header/`). The component goes in `pd/`; only non-`@Component` helpers/constants stay with the feature.
- The Vite `staticRegistry` plugin scans `src/components` and derives each importer path from the file location — moving a component to `pd/` updates the generated `src/lib/static-registry.ts` automatically (it is gitignored; never hand-edit it).
- When relocating an existing component into `pd/`, use `git mv` and fix any **relative** imports that now escape the moved folder. Imports via the `@/` alias and the generated registry need no change; only a typecheck/`vitest` run reliably catches the relative-path breakage.

### Metadata Class with Decorators

```typescript
import { Component, AttributeDefinition, RegionDefinition } from '@salesforce/storefront-next-runtime/design';

@Component('hero-banner', {
    name: 'Hero Banner',
    description: 'Full-width banner with image and CTA'
})
class HeroBannerMeta {
    @AttributeDefinition({ type: 'image' })
    image: string;

    @AttributeDefinition()
    headline: string;

    @AttributeDefinition({ type: 'url' })
    ctaUrl: string;

    @AttributeDefinition()
    ctaText: string;

    @AttributeDefinition({ type: 'boolean' })
    fullWidth: boolean;
}
```

### React Component

```typescript
// src/components/pd/hero-banner/index.tsx
export default function HeroBanner({ image, headline, ctaUrl, ctaText, fullWidth }) {
    return (
        <div className={cn('relative', fullWidth && 'w-full')}>
            <DynamicImage src={image} alt={headline} />
            <h1>{headline}</h1>
            {ctaUrl && <a href={ctaUrl}>{ctaText}</a>}
        </div>
    );
}
```

### Components with Server Data

If a component needs server data (e.g., product carousel):

```typescript
// Export a loader for the component
export function loader({ componentData, context }) {
    const clients = createApiClients(context);
    return clients.shopperProducts.getProducts({
        params: { query: { ids: componentData.productIds } }
    }).then(({ data }) => data);
}

// Optional fallback during loading
export function fallback() {
    return <CarouselSkeleton />;
}

// Component receives data as prop
export default function ProductCarousel({ data, ...props }) {
    return <Carousel products={data.products} />;
}
```

See [Component Registry Reference](references/COMPONENT-REGISTRY.md) for registry details.

## Design Mode

Detect when running inside Page Designer:

```typescript
import { isDesignModeActive, isPreviewModeActive } from '@salesforce/storefront-next-runtime/design/mode';

// In loaders
const isDesignMode = isDesignModeActive(request);
const isPreview = isPreviewModeActive(request);

// Root layout exposes pageDesignerMode in loader data
// 'EDIT' | 'PREVIEW' | undefined
```

## MCP Tools

Use the B2C DX MCP server tools for Page Designer development:

1. **`storefront_next_page_designer_decorator`** — Adds decorators to components (auto mode or interactive)
2. **`storefront_next_generate_page_designer_metadata`** — Generates metadata JSON for Business Manager
3. **`cartridge_deploy`** — Deploys cartridge to Commerce Cloud

### Typical Workflow

1. Add decorators to component (use `storefront_next_page_designer_decorator` with autoMode)
2. Generate metadata JSON (`storefront_next_generate_page_designer_metadata`)
3. Deploy cartridge (`cartridge_deploy`)

## Best Practices

1. **Place every `@Component` under `src/components/pd/`** — one folder per component; never co-locate with consuming feature code (see [File Location](#file-location-required)).
2. **Keep loaders synchronous** — Return promises for streaming
3. **Use registry** — Register components with proper `typeId`
4. **Handle design mode** — Adapt UI when `pageDesignerMode` is `'EDIT'` or `'PREVIEW'`
5. **Rebuild after changes** — Static registry regenerates at build time
6. **Use MCP tools** — Faster than hand-writing decorators and metadata

## Build Gotchas (read before adding a component)

Three mistakes break `pnpm build` (or silently produce the wrong descriptor) only at the cartridge-gen / `react-router build` stage (not in the editor), and have recurred:

1. **Enum `values` must be an inline array literal.** `Array.from(...)` or `[...] as T[]` are emitted as raw strings and fail B2C schema validation. See [Decorator Patterns → Enum values](references/DECORATOR-PATTERNS.md#enum-values-must-be-an-inline-array-literal-build-gotcha).
2. **`loaders.ts` may export only `loader` + erased types.** Any runtime value the client uses (`readMarkupField`-style helpers, formatters) must live in a sibling client-safe module — otherwise `loaders.ts` stays in the client bundle and its transitive `.server` import fails with `Server-only module referenced by client`. Same family: don't co-locate the `loader` value import with a `type` from `loaders` in a single declaration in `index.tsx`. See [Component Registry → server-only loaders](references/COMPONENT-REGISTRY.md#keep-server-only-loader-code-out-of-the-client-bundle-build-gotcha) — both the import-split fix and the runtime-export variant.
3. **All decorator arguments — `@Component`, `@PageType`, `@RegionDefinition`, `@AttributeDefinition` — must be inline object/array literals.** `sfnext generate-cartridge` is AST-based; it cannot resolve imported constants, spreads, or `as` casts at AST time. Using an imported `STOREFRONT_PAGE_TYPE` constant produces a silent fallback descriptor (filename derived from the class name, empty `region_definitions`, generic `description: "Custom page type: <ClassName>"`) — NOT a build error.

## Page Types and PD preview routing

Page types (vs component types) declare a Page Designer page descriptor — region layout, exclusions, BM-facing name. They live on a metadata class decorated with `@PageType` + `@RegionDefinition`, co-located with the React Router route that owns the page.

**Two URL substitution sources** in the descriptor's `route` field:
- `:siteId`, `:localeId` — always available.
- Aspect-attribute tokens (`:productId` from `pdp` aspect, `:categoryId` from `plp`) — substituted by PD from the page's aspect-assignment in BM.

The page's own `content-id` is **not** a substitutable token. A descriptor with `supportedAspectTypes: []` and a `:foo` path token in `route` produces a broken preview iframe URL (literal `:foo` stays in the URL → empty canvas in PD with storefront chrome visible around it).

**For pages with no aspect** (e.g. `modulePage`, `storePage`):
- Descriptor `route` is **static** (no path tokens). PD appends `?pageId=<contentId>` to the iframe URL automatically.
- Route file uses the `_empty.<slug>.tsx` shape — see your project's `sfnext/src/routes/_empty.module-page.tsx` and `sfnext/src/routes/_empty.storefront-page.tsx`:
  - `_empty.` prefix → no `_app` storefront chrome leaks into the preview canvas.
  - Loader 404s when neither `isDesignModeActive(args.request)` nor `isPreviewModeActive(args.request)` — direct shopper hits MUST NOT render this URL.
  - Loader reads `args.request.url.searchParams.get('pageId')` and calls `fetchPageWithComponentData(args, { pageId })`.

**When legacy SFRA used a custom-attribute-driven controller** for a PD page (e.g. `Category.c_pageDesignerId` → `PageMgr.getPage(...)` in `Search.js`), port the same attribute resolution into the **consumer route's** loader (e.g. `_app.category.$categoryId.tsx`). The `_empty.<slug>.tsx` route is then a preview-only surface; production traffic never sees it. Do NOT add an aspect to the standalone descriptor just to make preview work — the `_empty.` pattern already covers it.

Rules:
- **Inline literals only** in `@PageType` and `@RegionDefinition` arguments (gotcha #3).
- **Filename = camelCase(`@PageType.name`)** — pick `name` deliberately if a legacy library export references a specific `page.type_id` (e.g. `'Store Page'` → `storePage.json` matches legacy `page.storePage`).
- **Regression guard:** import the generated JSON in a unit test and assert `getPageTypeMetadata(...)` + `getRegionDefinitions(...)` match it. Drift = generator bug or someone hand-edited the JSON.
- **Run the generator** after editing decorators: `pnpm cartridge:generate` should print `PASS: pages/<name>.json (pagetype)` and `N/N file(s) valid, 0 error(s)`.
